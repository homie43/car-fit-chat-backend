Проектирование чат-сервиса по подбору автомобиля (CarFit Chat). Копылов В.В.
1. Описание сервиса и его бизнес задачи.
CarFit Chat - закрытый онлайн-сервис подбора автомобиля в формате чата. Пользователь проходит регистрацию/авторизация и в приватной зоне общается с AI-ассистентом как с консультантом: описывает пожелания, бюджет, условия эксплуатации, предпочтения по марке/модели/характеристикам. Ассистент задаёт уточняющие вопросы, извлекает из диалога структурированные параметры и предлагает 1-3 подходящих варианта из каталога автомобилей, импортированного из XML в PostgreSQL.
Дополнительно сервис умеет показать стоимость владения/обслуживания (TCO) только при наличии VIN (17 символов), который присылает пользователь - расчёт выполняется через https://www.auto.dev/ TCO API с кешированием результата.
Сервис поддерживает интерфейс и ответы на RU/EN, включает базовую модерацию нежелательного контента и имеет простую административную панель для просмотра пользователей, диалогов и технических логов.
Кто пользуется:
* частные покупатели авто (первый авто / смена авто / переезд / семейные задачи);
* пользователи, которым важны эксплуатационные расходы и прозрачность владения;
* пользователи, которым нужен онлайн “консультант”, но без взаимодействия с менеджером.
Когда это нужно:
* выбор автомобиля “под задачу” (город/трасса/семья/поездки/работа);
* сужение поиска до 1 - 3 вариантов;
* оценка или проверка стоимости владения по конкретному VIN.
Основные бизнес-задачи:
1. Снизить время выбора автомобиля.
2. Повысить качество выбора: учитывать ключевые параметры (тип коробки, мощность, страна/марка, цвет как пример, бюджет, сценарий эксплуатации).
3. Дать оценку стоимости владения по конкретному экземпляру (VIN -> TCO), чтобы пользователь мог сравнить варианты и снизить риск “дорогой эксплуатации”.
4. Сделать сервис доступным 24/7 без нагрузки на менеджеров.


2. Описание ключевых разделов и функционала
Сервис CarFit Chat состоит из публичной части (аутентификация) и закрытой части, доступной только авторизованным пользователям. Основная логика сервиса сосредоточена вокруг чат-интерфейса и AI-ассистента. Дополнительно предусмотрена административная панель для просмотра истории сообщений и управления диалогами.
2.1. Публичный раздел (Аутентификация).
Функционал
* Регистрация пользователя по email и паролю.
* Авторизация (логин) с использованием логина и пароля.
* Обновление сессии через refresh-токен.
Особенности
* Доступ к сервису возможен только после авторизации.
* Используется классическая схема access + refresh token.
* После успешной авторизации пользователь автоматически перенаправляется в чат-интерфейс.
2.2. Пользовательский(закрытый) раздел


2.2.1. Чат-интерфейс (основной экран сервиса)

Основной пользовательский интерфейс, в котором происходит взаимодействие с AI-ассистентом.
Функционал
* Один активный диалог на пользователя.
* Отправка текстовых сообщений пользователем.
* Получение ответов ассистента в режиме стриминга.
* Отображение истории сообщений (user / assistant / system).
* Поддержка RU/EN (в зависимости от пользователя или запроса).

Логика работы
   * Пользователь формулирует запрос в свободной форме.
   * Сообщение проходит базовую модерацию.
   * Сообщение передаётся AI-ассистенту.

   * Ассистент:
      * анализирует всю историю диалога,
      * извлекает структурированные предпочтения,
      * при необходимости задаёт уточняющие вопросы,
      * формирует рекомендации.



2.2.2. AI-ассистент (логика подбора)
Имитация работы автомобильного консультанта с определенными правилами и ограничениями.
Основные функции ассистента
         * Извлечение из диалога структурированных предпочтений пользователя (марка, модель, коробка передач, мощность, страна, цвет и др.).
         * Контроль полноты данных: если заполнено менее 3 ключевых параметров - ассистент задаёт 1 - 3 уточняющих вопроса.
         * Формирование рекомендаций:
         * строго на основе данных, доступных в каталоге автомобилей (PostgreSQL);
         * 1 - 3 варианта;
         * с текстовым объяснением, почему эти варианты подходят.
         * Работа с отсутствующими данными: если данных по параметру или автомобилю нет - ассистент явно сообщает об этом.

Ограничения
            * Ассистент не придумывает характеристики автомобилей.
            * Ассистент не использует внешние источники для подбора (только БД сервиса).
            * Ассистент не рассчитывает стоимость владения без VIN.

2.2.3 Расчёт стоимости владения (TCO)(пока не знаю, нужно ли это выводить в отдельный пункт)
Предоставление пользователю прозрачной оценки стоимости эксплуатации автомобиля.
Функционал
               * При отсутствии VIN ассистент:
               * запрашивает VIN (17 символов);
               * объясняет, что расчёт TCO возможен только по VIN.
               * При наличии VIN:
               * валидация формата VIN;
               * запрос к внешнему API auto.dev;
               * кеширование результата;
               * возврат пользователю одной агрегированной цифры (например, общая стоимость владения за период) с валютой.
               * Обработка ошибок:
               * недоступность API;
               * превышение лимитов;
               * некорректный VIN.
2.3.Профиль пользователя (минимальный)
Функционал
               * Хранение базовой информации пользователя:
               * email,
               * passwordHash, 
               * role,
               * createdAt,
               * language?,
               * name?.
               * Хранение предпочтений пользователя в структурированном виде (JSON), обновляемых на основе диалога.
               * Определение роли пользователя (user / admin).
2.4. Админ-раздел
Обеспечение контроля, поддержки и отладки сервиса без вмешательства в код. Доступ к разделу будет строго ограничен ролью admin и только через аутентификацию с ролями.
Функционал
               * Управление пользователями
               * Просмотр списка зарегистрированных пользователей.
               * Просмотр базовой информации по пользователю.
               * Сброс пароля пользователя.
               * Просмотр роли пользователя.
               * Управление диалогами
               * Просмотр списка диалогов.
               * Просмотр истории сообщений конкретного диалога.
               * Удаление диалога.
               * Экспорт истории диалога (например, JSON/CSV).
               * Логи и аудит
               * Просмотр логов в реалтайме:
               * запросов и ответов LLM;
               * запросов к auto.dev;
               * событий модерации.
               * Фильтрация логов по пользователю, диалогу, типу провайдера.

2.5. Модерация контента (MVP)
Для обеспечения безопасности и соблюдения стандартов сервиса, система будет реализовывать двухуровневую модерацию контента для проверки сообщений, поступающих от пользователей и передаваемых AI-ассистенту.
                  * Pre-moderation: Проверка входящих сообщений от пользователя на наличие запрещённых слов, конфиденциальной информации, спама и превышения лимитов. Сообщения, нарушающие правила, не отправляются в LLM и возвращаются пользователю с уведомлением о нарушении.

                  * Post-moderation: Проверка сгенерированных ответов LLM на токсичность, запрет контента и конфиденциальную информацию перед отправкой пользователю. Если ответ содержит нарушение, он заменяется на безопасный шаблон.

                  * Логирование инцидентов: Все блокированные или отредактированные сообщения и ответы записываются в provider_logs для аудита и анализа.

                  * Защита от вредоносных действий: Используются guardrails в промптах и дополнительные проверки для защиты от вредоносных запросов.
2.6. Сквозные нефункциональные особенности
                     * Стриминг ответов ассистента для улучшения UX.
                     * Централизованная обработка ошибок.
                     * Логирование всех внешних интеграций.
                     * Предсказуемое поведение ассистента за счёт жёстких правил.


3. Описание структуры БД
База данных хранит:
                     1. пользователей и их профиль/предпочтения,
                     2. диалоги и историю сообщений,
                     3. каталог автомобилей, импортированный из XML,
                     4. кеш результатов TCO по VIN,
                     5. технические логи (LLM / auto.dev / moderation) для админки и аудита.
Все PK - uuid. Временные поля - createdAt/updatedAt с автоматическим заполнением. JSON хранится в jsonb.
3.1. Пользователи
users - это учетные записи и базовые настройки пользователя.
Минимальные поля (MVP):
                     * id (PK, uuid)
                     * email (unique, индекс)
                     * passwordHash
                     * role (user | admin) - для защиты админки
                     * createdAt - дата/время создания пользователя (когда зарегистрировался)
                     * updatedAt - дата/время последнего изменения записи пользователя(когда обновляется preferences jsonb, админ сделал reset password (если меняется passwordHash)).
                     * language (ru | en, nullable) - язык UI/ответов
                     * name (nullable) - опционально
                     * preferences (jsonb) - извлечённые предпочтения пользователя из диалога
Пример структуры: 

{
 "marka": "...",
 "model": "...",
 "power": "...",
 "kpp": "...",
 "yearFrom": 2019
}
	

3.2. Диалоги и сообщения
dialogs - один диалог на пользователя.
                     * id (PK)
                     * userId (unique, FK → users.id) — обеспечивает “1 диалог на пользователя”
                     * createdAt - дата/время создания диалога,
                     * updatedAt - дата/время изменения диалога
Индексы: dialogs.userId - unique

messages - история сообщений.
                     * id (PK)
                     * dialogId (FK → dialogs.id)
                     * role (user | assistant | system)
                     * content (text)
                     * createdAt- дата/время отправки конкретного сообщеения
                     * moderationStatus ('OK' | 'BLOCKED')
                     * blockedReason (nullable) - причина блокировки при нарушении модерации
Индексы: messages.dialogId, createdAt (для быстрого получения истории в порядке времени).
Мы храним только текст сообщения в messages. Структурные данные (извлечённые предпочтения, модерация, сырые запросы/ответы провайдеров) - в users.preferences и provider_logs.


3.3. Каталог автомобилей (импортируем из xml)
Цель каталога - давать рекомендации “по справочнику” и не выдумывать характеристик.
При этом единица рекомендации для пользователя - модель, а внутри показываем модификации (variants).
Справочники:
car_brands
                     * id (PK)
                     * code (например THAIRUNG, nullable/unique при наличии) - внешний “машинный” идентификатор из XML, если есть.
                     * name (например Thairung)

Индексы: 
                        * car_brands.name (btree)
                        * car_brands.code unique (если всегда заполнен)

car_models
                           * id (PK)

                           * brandId (FK → car_brands.id)
                           * name (например TRANSFORMER)
                           * slug (nullable) — удобный ключ для фронта/URL (опционально)

Индексы:
                              * car_models.brandId
                              * car_models.name
                              * (опционально) unique (brandId, name) чтобы не было дублей

Модификации (variants/trims):
car_variants (это сущность “modification” из XML)
                                 * id (PK)
                                 * modelId (FK → car_models.id)
                                 * name (пример: 2.8d AT (177 л.с.) 4WD)
                                 * bodyType (nullable) - из <body_type>
                                 * yearFrom (int, nullable)
                                 * yearTo (int, nullable; null если “по н.в.”)
                                 * powerText (text, nullable) - как текст (из name при импорте, если получилось)
                                 * kppText (text, nullable) - как текст (из name при импорте, если получилось)
                                 * meta (jsonb) - сырые поля из XML, которые не используем как колонки в MVP (пример: configuration_id, tech_param_id, folder_id, generation, и т.д.)
                                 * createdAt (timestamp) — когда запись создана в БД (полезно для повторных импортов/аудита)
                                 * updatedAt (timestamp) — когда запись обновлялась (например при ре-импорте)

Почему так: 
                                    * name + meta гарантируют, что мы ничего не теряем из XML.
                                    * yearFrom/yearTo позволяют честно фильтровать по годам.
                                    * powerText/kppText можно заполнить очень простым парсером из name (и при ошибке оставить null) - это даёт удобный поиск без усложнения схемы.

Индексы:
                                       * car_variants.modelId
                                       * car_variants.yearFrom, yearTo
                                       * (опционально) trigram/GIN индекс на name для быстрого поиска по строке (если будет много данных)

Важно: country и color не храним в каталоге, так как их нет в XML. Они могут оставаться только как “желания пользователя” (в preferences), и ассистент будет честно говорить, что в каталоге эти параметры недоступны.


3.4. Комплектации (из <complectations>)
Сделать 2 таблицы:
car_complectations(id, extId, name)
Зачем и что хранит:
                                          * справочник уникальных комплектаций из XML
                                          * extId - внешний id из XML (например 20078505)
                                          * name - название (например Titanium, Sport)

Ограничения/индексы:
                                             * unique(extId) - чтобы одна и та же комплектация не дублировалась
                                             * (опционально) index(name) - если понадобится поиск по названию

car_variant_complectations(variantId, complectationId)
                                                * связь many-to-many между модификациями и комплектациями
Ограничения/индексы:
                                                * PRIMARY KEY (variantId, complectationId) (или unique(variantId, complectationId))
                                                * index(variantId)
                                                * index(complectationId)


3.5. TCO (кеш результатов auto.dev по VIN)
tco_cache
                                                * id (PK)
                                                * vin (unique)
                                                * tcoValue (numeric) — одна агрегированная цифра, которую мы показываем (фиксируем заранее, например “total cost over 5 years”)
                                                * currency (text)
                                                * raw (jsonb) — полный ответ TCO API
                                                * vinDecoded (jsonb) — результат VIN decode (для валидации/инфо)
                                                * fetchedAt
                                                * expiresAt (fetchedAt + 30 days)
Индексы:
                                                * tco_cache.vin unique
                                                * tco_cache.expiresAt (для очистки просроченного кеша)


3.6. Логи провайдеров и модерации (для админки)
provider_logs - единая таблица логов интеграций и модерации.
                                                * id (PK)
                                                * kind (LLM | AUTO_DEV | MODERATION)
                                                * userId (nullable)
                                                * dialogId (nullable)
                                                * request (jsonb) - сырой запрос (с маскированием чувствительных данных)
                                                * response (jsonb) — сырой ответ (с маскированием)
                                                * status (text/int)
                                                * latencyMs (int)
                                                * createdAt

Индексы:
                                                   * provider_logs.kind, createdAt
                                                   * provider_logs.userId, createdAt
                                                   * provider_logs.dialogId, createdAt


4. Mini-ERD (сущности и связи)
Основные доменные связи
                                                   * users (1) → (1) dialogs - один пользователь имеет один диалог (ограничение dialogs.userId UNIQUE).

                                                   * dialogs (1) → (N) messages - диалог состоит из множества сообщений (пользователь/ассистент/системные).

Каталог авто (из XML)
                                                      * car_brands (1) → (N) car_models - бренд содержит несколько моделей.
                                                      * car_models (1) → (N) car_variants - модель содержит несколько модификаций/вариантов.

Комплектации (если используем как сущности)
                                                         * car_variants (N) ↔ (M) car_complectations через car_variant_complectations - одна модификация может иметь несколько комплектаций, и одна комплектация может встречаться у разных модификаций.

Интеграции и логи
                                                            * users (0..1) → (N) provider_logs
                                                            * dialogs (0..1) → (N) provider_logs - логи могут быть привязаны к пользователю и/или диалогу (а могут быть системными, если нужно).

TCO кеш
                                                               * tco_cache - отдельная сущность по vin (не связана FK с каталогом, потому что каталог без VIN).


car_brands (1) → (N) car_models → (N) car_variants — это иерархия каталога, а рекомендации идут на уровне car_models с отображением car_variants как деталей.
5. Индексы под REST/Socket сценарии
5.1. Auth / Me
users
                                                               * UNIQUE (email) - логин по email
                                                               * (опционально) INDEX (role) - если часто фильтруешь пользователей в админке (обычно не нужно)


5.2. Чат: получение диалога и сообщений
Эндпоинты:
                                                               * GET /dialogs/me
                                                               * GET /dialogs/me/messages
dialogs
                                                               * UNIQUE (userId) - найти диалог по пользователю за O(logN)
                                                               * INDEX (updatedAt) - если в админке сортируешь по активности (часто нужно)
messages
                                                               * INDEX (dialogId, createdAt) - критический индекс
Даст:
                                                                  * быстрый выбор истории одного диалога по времени
                                                                  * стабильный порядок сообщений
                                                                  * (опционально) INDEX (createdAt) - если будут отчёты/экспорт “по времени” без dialogId (обычно не надо)


5.3. Каталог авто
Эндпоинты:
                                                                  * GET /cars/brands
                                                                  * GET /cars/models?brand=
                                                                  * GET /cars/search?marka=&model=&power=&kpp=&...
car_brands
                                                                  * INDEX (name) - сортировка/поиск бренда
                                                                  * UNIQUE (code) - если используешь code как стабильный ключ (и он реально всегда есть)

car_models
                                                                     * INDEX (brandId) - получить модели бренда
                                                                     * INDEX (name) - поиск модели по названию
                                                                     * UNIQUE (brandId, name) - защита от дублей импорта
car_variants
                                                                     * INDEX (modelId, yearFrom, yearTo) - основной “рабочий” индекс (варианты модели + фильтр по годам)
                                                                     * (опционально) trigram/GIN на name - если реально понадобится “поиск как в гугле” по строке модификации
                                                                     * (опционально) INDEX (kppText) и/или INDEX (powerText) - только если фильтр по ним станет частым и точным. Для MVP обычно хватает ILIKE + modelId.

Уникальность против дублей (важно для импорта):
                                                                        * UNIQUE (modelId, name, yearFrom, yearTo)
5.4. Комплектации
car_complectations
                                                                        * UNIQUE (extId) - внешний ID из XML как стабильный ключ
                                                                        * (опционально) INDEX (name) - если будет поиск по названию
car_variant_complectations
                                                                        * PRIMARY KEY (variantId, complectationId) (или UNIQUE)

6.2. Контекст данных и состояние диалога
Где хранится состояние:

LLM не хранит состояние у себя - вся память диалога строится:

Язык ответа ассистента определяется следующим образом:

                                                                              * если users.language отсутствует, язык определяется по языку первого пользовательского сообщения и сохраняется в профиль пользователя для последующих ответов.
6.2.1. Preferences JSON schema (MVP)        
Структура preferences (MVP):


{
 "marka": "string | null",
 "model": "string | null",
 "budget": "number | null",
 "power": "string | null",
 "kpp": "string | null",
 "yearFrom": "number | null",
 "yearTo": "number | null"

Правило обновления preferences:

                                                                              * уверенность определяется тем, что:
                                                                              * значение явно указано пользователем,
                                                                              * либо подтверждено в ходе диалога,
                                                                              * и отличается от ранее сохранённого значения;
                                                                              * частично заполненные или предположительные данные не перезаписывают существующие.

6.4. Socket.io (чат и стриминг)
Авторизация

                                                                                       * Backend валидирует токен и связывает socket с userId.

}
	

Server → Client


chat:assistant_start {
 messageId
}

}

}

6.4.1. Основной поток обработки пользовательского сообщения:
                                                                                       1. Клиент отправляет событие chat:user_message с текстом сообщения.

                                                                                       2. Backend проверяет наличие активного диалога:
                                                                                          * если диалог отсутствует — создаётся dialog, связанный с пользователем.

                                                                                             3. Сообщение проходит pre-moderation:
                                                                                             * при нарушении сообщение сохраняется в messages со статусом BLOCKED,
                                                                                             * LLM не вызывается,
                                                                                             * пользователю отправляется вежливый системный ответ.

                                                                                                4. При успешной pre-moderation сообщение сохраняется в messages со статусом OK.

                                                                                                5. Backend формирует контекст для LLM:
                                                                                                   * история сообщений из messages,
                                                                                                   * текущие предпочтения пользователя из users.preferences,
                                                                                                   * системные правила ассистента.

                                                                                                      6. Из текста сообщения извлекается VIN (если присутствует):
                                                                                                      * при валидном VIN запускается VIN decode и TCO (см. ниже).

                                                                                                         7. LLM вызывается через aiService:
                                                                                                         * формирует обновлённые preferences (внутренне),
                                                                                                         * принимает решение: задать уточняющие вопросы или сформировать рекомендации,
                                                                                                         * при необходимости инициирует поиск через /cars/search.

                                                                                                            8. Ответ ассистента стримится клиенту через Socket.io (assistant_start → assistant_delta).

                                                                                                            9. После завершения генерации:
                                                                                                               * финальный текст сохраняется в messages,
                                                                                                               * preferences обновляются при наличии новых подтверждённых данных,
                                                                                                               * отправляется событие chat:assistant_done.


При стриминге ответа ассистента:
                                                                                                               * промежуточные assistant_delta не сохраняются в базе данных;
                                                                                                               * в messages сохраняется только финальный текст ответа после события chat:assistant_done.



6.5. Роль и задачи LLM
LLM - диалоговый оркестратор и объясняющий слой, но не источник данных.
Основные задачи LLM:
                                                                                                                  1. Ведение диалога в естественной форме (RU/EN).
                                                                                                                  2. Извлечение структурированных предпочтений.
                                                                                                                  3. Контроль полноты данных:
                                                                                                                  * если < 3 ключевых полей → задать 1–3 уточняющих вопроса.
                                                                                                                  4. Управление поиском:
                                                                                                                  * формирует параметры,
                                                                                                                  * вызывает /cars/search через backend.
                                                                                                                  5. Формирование рекомендаций:
                                                                                                                  * 1-3 модели,
                                                                                                                  * с объяснением “почему подходят”,
                                                                                                                  * строго по данным из БД.
                                                                                                                  6. Работа с VIN/TCO:
                                                                                                                  * VIN извлекается из текста пользовательского сообщения с помощью регулярного выражения (17 символов, без I/O/Q).
                                                                                                                  * При некорректном формате VIN пользователю возвращается сообщение о неверном идентификаторе, запросы к auto.dev не выполняются.
                                                                                                                  * При валидном VIN:
                                                                                                                  * сначала выполняется VIN decode,
                                                                                                                  * затем запрашивается TCO,
                                                                                                                  * результаты передаются LLM как дополнительный контекст для формирования ответа.

Ограничения LLM:
                                                                                                                     * не придумывает характеристики авто;
                                                                                                                     * не использует внешние источники;
                                                                                                                     * не считает TCO без VIN.
6.6. Retrieval из PostgreSQL
Подход
                                                                                                                     * LLM не видит БД напрямую.
                                                                                                                     * Backend предоставляет контролируемый API /cars/search.

Стратегия поиска:
                                                                                                                        1. Пробуем точные фильтры (brand/model/year/kpp/power).
                                                                                                                        2. Если данных мало - fallback через ILIKE по variant.name.

Формат данных для LLM
Короткие карточки, например:
Brand: Toyota
Model: Camry
Years: 2019-2022
Variants:
- 2.5 AT (181 hp), Sedan
- 3.5 AT (249 hp), Sedan
	

6.7. Модерация и безопасность в потоке
Pre-moderation
                                                                                                                           * Проверка входящего текста.
                                                                                                                           * Нарушение → сообщение сохраняется как “moderationStatus = BLOCKED”, LLM не вызывается.
                                                                                                                           * Пользователь получает вежливый ответ.
                                                                                                                           * Инцидент логируется (provider_logs).

Post-moderation
                                                                                                                              * Проверка финального ответа LLM.
                                                                                                                              * При нарушении:
                                                                                                                              * ответ заменяется безопасным шаблоном,
                                                                                                                              * шаблон сохраняется в messages,
                                                                                                                              * событие логируется.
Формат ответа /cars/search (MVP):
                                                                                                                              * бренд и модель автомобиля,
                                                                                                                              * диапазон годов выпуска,
                                                                                                                              * 2-3 модификации (variants) с:
                                                                                                                              * названием,
                                                                                                                              * типом кузова,
                                                                                                                              * коробкой передач (если доступно),
                                                                                                                              * мощностью (если доступно).

Ответ не содержит лишних технических или сырых данных из XML и предназначен для компактной передачи в LLM.


6.8. Логирование и наблюдаемость

В provider_logs:

7.4.2. Типизация данных
                                                                                                                                                            * Все REST ответы и запросы типизируются через TypeScript интерфейсы.
                                                                                                                                                            * Socket.io события типизируются (client → server, server → client) единым контрактом.
                                                                                                                                                            * extractedPreferencesJson используется только как read-only debug payload.




7.5. Socket.io client: подключение и обработка событий
7.5.1. Подключение
Socket создаётся только когда:
                                                                                                                                                            * пользователь авторизован,
                                                                                                                                                            * есть accessToken.
Подключение:
                                                                                                                                                            * io(BACKEND_URL, { auth: { token: accessToken } })
На backend:
                                                                                                                                                            * валидация токена,
                                                                                                                                                            * привязка socket → userId.
При истечении access token:
                                                                                                                                                            * для REST:
                                                                                                                                                            * RTK Query перехватывает 401,
                                                                                                                                                            * вызывает POST /auth/refresh,
                                                                                                                                                            * повторяет оригинальный запрос.
                                                                                                                                                            * для Socket.io:
                                                                                                                                                            * при ошибке авторизации socket disconnect,
                                                                                                                                                            * выполняется refresh,
                                                                                                                                                            * socket пересоздаётся с новым access token.
Если refresh неуспешен → logout и редирект на /login.




7.5.2. Отправка сообщения
UI → socket.emit('chat:user_message', { dialogId, text })
7.5.3. Приём стриминга
Обработчики:
                                                                                                                                                            * chat:assistant_start({ messageId })
                                                                                                                                                            * создать в UI список сообщений новый message ассистента с пустым текстом
                                                                                                                                                            * streaming.isStreaming = true
                                                                                                                                                            * chat:assistant_delta({ messageId, deltaText })
                                                                                                                                                            * найти message по id и дописать deltaText
                                                                                                                                                            * показывать “typing” состояние
                                                                                                                                                            * chat:assistant_done({ messageId, finalText, extractedPreferencesJson })
                                                                                                                                                            * заменить текст на финальный finalText (или финализировать дописанное)
                                                                                                                                                            * streaming.isStreaming = false
                                                                                                                                                            * extractedPreferencesJson можно не отображать пользователю; использовать для debug (опционально)
                                                                                                                                                            * chat:error({ code, message })
                                                                                                                                                            * показать snackbar/toast
                                                                                                                                                            * lastError = { code, message }
                                                                                                                                                            * остановить streaming если нужно

7.5.4. Сохранение сообщений
Frontend не сохраняет сообщения в БД напрямую.
Источник истины - backend, который пишет messages.
На фронте сообщения хранятся как UI-коллекция:
                                                                                                                                                               * начальная инициализация из GET /dialogs/me/messages,
                                                                                                                                                               * после перезагрузки страницы история восстанавливается через GET /dialogs/me/messages.
                                                                                                                                                               * новые сообщения добавляются/обновляются через Socket events.
7.5.5. Отображение moderationStatus
Если message.moderationStatus = BLOCKED:
                                                                                                                                                               * сообщение пользователя отображается в UI с визуальной пометкой “заблокировано”,
                                                                                                                                                               * текст не редактируется на клиенте,
                                                                                                                                                               * системный ответ (assistant/system) отображается как обычное сообщение.


7.6. Auth flow на фронте (access + refresh)
Базовое правило
При старте приложения:

                                                                                                                                                               1. вызвать GET /me

                                                                                                                                                               2. если 401 → вызвать POST /auth/refresh

                                                                                                                                                               3. если refresh успешен → повторить GET /me

                                                                                                                                                               4. если refresh неуспешен → logout → /login

При любом REST запросе (через RTK Query baseQuery)
                                                                                                                                                                  * если сервер вернул 401:
                                                                                                                                                                  * попытка refresh,
                                                                                                                                                                  * повтор запроса,
                                                                                                                                                                  * если снова 401 → logout.
Для socket
                                                                                                                                                                  * если socket disconnect по причине auth:
                                                                                                                                                                  * выполнить refresh,
                                                                                                                                                                  * пересоздать socket с новым access token.
7.7. Экран чата: логика
Страница /chat при загрузке:
                                                                                                                                                                  1. GET /dialogs/me
                                                                                                                                                                  * если диалог отсутствует (он создаётся на первом сообщении):
                                                                                                                                                                  * UI держит dialogId = null до первого chat:user_message
                                                                                                                                                                  * либо backend возвращает “виртуальный dialog” (но ты не фиксировал это - значит держим null)

                                                                                                                                                                     2. GET /dialogs/me/messages
                                                                                                                                                                     * грузим всю историю одним запросом
                                                                                                                                                                     * рендерим список сообщений по createdAt ASC

Отправка сообщения пользователем:
                                                                                                                                                                        3. пользователь вводит text → chat:user_message { dialogId, text }

                                                                                                                                                                        4. UI сразу добавляет оптимистично user-message, а при ошибке показываем toast. 
                                                                                                                                                                        5. если backend заблокировал сообщение (pre-moderation):

                                                                                                                                                                           * в истории будет moderationStatus = BLOCKED
                                                                                                                                                                           * UI отображает это сообщение как заблокированное + системный ответ (который backend отправит)

                                                                                                                                                                              6. если сообщение принято:
                                                                                                                                                                              * UI получает assistant_start/delta/done

Важное правило из проектирования
                                                                                                                                                                                 * assistant_delta не пишутся в БД - UI живёт на стриминге, но при перезагрузке всегда восстановится по финальным сообщениям из истории.


7.8. Отображение blocked сообщений (прямая связка с БД)
Так как в messages есть:
                                                                                                                                                                                 * moderationStatus: 'OK' | 'BLOCKED'
                                                                                                                                                                                 * blockedReason?: string

UI правило:
                                                                                                                                                                                    * если moderationStatus = BLOCKED:
                                                                                                                                                                                    * сообщение пользователя отображается как “заблокировано”
                                                                                                                                                                                    * текст ассистента/системы отображается как “не могу обработать запрос” (ожидается, что backend создаёт системный message)




7.9. Admin UI: страницы и данные
/admin/users
                                                                                                                                                                                    * GET /admin/users
                                                                                                                                                                                    * таблица пользователей (email, role, createdAt)

                                                                                                                                                                                    * просмотр request/response (маскированных)

7.10. Что фронт НЕ делает (явно фиксирую границы для LLM)
Frontend:
                                                                                                                                                                                       * не выбирает автомобили,
                                                                                                                                                                                       * не решает задавать вопросы или рекомендовать,
                                                                                                                                                                                       * не валидирует бизнес-правила подбора,
                                                                                                                                                                                       * не обращается к auto.dev напрямую,
                                                                                                                                                                                       * не формирует prompt,
                                                                                                                                                                                       * не хранит долгосрочное состояние диалога (только отображает и кеширует через RTK Query).

8. Промпты (в процессе, сейгодня доделываю)
1. Определение модели: deepSeek
Для выполнения задач, связанных с анализом запросов пользователя, извлечением структурированных данных и генерацией рекомендаций, лучше всего подойдет модель, которая умеет работать с диалоговыми данными и извлекать важные параметры из свободного текста. deepSeek - это подходящая модель для данного случая, так как она может эффективно извлекать информацию из неструктурированных текстов, таких как сообщения пользователей.
2. Пример структуры промпта для AI-ассистента:
Задача 1: Извлечение предпочтений пользователя
Промпт:
"Проанализируй сообщение пользователя и извлеки из него информацию о его предпочтениях для подбора автомобиля. Учитывай такие параметры, как марка, модель, год выпуска, мощность, тип коробки передач и бюджет. Если этих данных недостаточно для начала подбора, задай уточняющие вопросы. Пример сообщения: 'Мне нужен автомобиль для поездок по городу с автоматической коробкой передач, бюджет до 1.5 миллионов.'"
Задача 2: Обработка и уточнение данных
Промпт:
"Если в сообщении пользователя недостаточно информации для точного подбора автомобиля (например, отсутствует марка или модель), задай уточняющие вопросы для получения недостающих данных. Пример вопросов: 'Какая марка автомобиля вас интересует?', 'Какой тип кузова вы предпочитаете?'"
Задача 3: Формирование рекомендаций
Промпт:
"На основе извлеченных предпочтений и данных о доступных автомобилях из базы данных, предложи 1-3 подходящих варианта. Объясни, почему эти автомобили подходят пользователю, с учетом его предпочтений по типу коробки передач, мощности, марке и бюджету. Пример: 'Мы подобрали три варианта, которые соответствуют вашему запросу...'."
Задача 4: Валидация VIN для расчета TCO
Промпт:
"Если в сообщении пользователя содержится VIN (17 символов), проверь его формат и, если он валиден, запроси расчет стоимости владения через auto.dev API. В случае некорректного VIN сообщи пользователю о проблемах с идентификатором. Пример: 'Ваш VIN некорректен, пожалуйста, проверьте его и попробуйте снова.'"
Задача 5: Модерация контента
Промпт:
"Перед тем как передать текст от пользователя к LLM, проведи его проверку на спам, токсичность и конфиденциальную информацию. Если сообщение нарушает правила, заблокируй его и уведомь пользователя. Пример: 'Ваше сообщение нарушает правила, пожалуйста, исправьте его.'"
3. Декомпозиция задач:
Для разработки можно использовать один большой промпт с декомпозицией на задачи, который будет поочередно решать каждую из описанных задач. Пример такого промпта:
Основной промпт для разработки:
"Ты AI-ассистент для подбора автомобиля. Каждый раз, когда пользователь отправляет запрос, выполняй следующие шаги:
                                                                                                                                                                                       1. Прочитай сообщение пользователя и извлеки из него предпочтения (марка, модель, мощность, год, тип коробки передач, цвет, бюджет и т.д.).

                                                                                                                                                                                       2. Если информации недостаточно (менее 3 ключевых параметров), задай 1-3 уточняющих вопроса.

                                                                                                                                                                                       3. На основе предпочтений и данных о автомобилях из базы данных, предложи 1-3 подходящих варианта.

                                                                                                                                                                                       4. Если в запросе присутствует VIN, проверь его и запроси расчет стоимости владения через auto.dev API, если VIN валиден.

                                                                                                                                                                                       5. Пройдись через модерацию и отклоняй сообщения с нарушением правил (спам, токсичность)."

Этот промпт обеспечит логичную и последовательную работу AI-ассистента, позволяя организовать все процессы в рамках одного диалога.
